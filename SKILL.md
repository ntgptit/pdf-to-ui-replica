# PDF to UI replica

Rebuild PDF pages as a **reusable component template** whose geometry, colours, strokes and text spacing are *measured* from the PDF (not eyeballed) and *verified* by two independent layers. Learned on a Korean language workbook (Sejong 4A); the example in `examples/sejong-workbook/` is that run.

Do not guess and do not judge by a small whole-page screenshot: a whole-page overlay hides 1–3 px errors. Measure numbers, then zoom per part.

## Supported stack
**React + shadcn/ui + Tailwind CSS v4** (detected from `components.json` and `package.json`; `gate scope` refuses other stacks for now, they come later). How the sheet and reading views, typography and artwork are written in this stack: [13-react-shadcn-tailwind.md](references/13-react-shadcn-tailwind.md). The project's own rules (token guards, folders, control sizes) still win.

## Shared components are mandatory (owner, 2026-11-24)
Every pattern a page repeats (example label, answer line with its lead arrow or speaker, rule, frame, item number, table header…) is **one** kit primitive used by every page; a block never draws its own. Books differ in style, so the primitive's contract is shared (`core/kit/contract.ts`) and each book implements the whole kit once in its style. Two copies of a pattern drift (a label whose text sits lower on one page, an arrow that rides on the rule on one page only: knowhow KH-011). Each book's definition is typed (`as const satisfies BookStyle` or `defineBook`, rule L20) and the registry gives `BookId`; a series kit shared by books of one series is allowed only from 3 books (rule L19, `14-module-layout.md` §7). Enforced by `pdfmeasure structure` (rules L16-L20) and `pdfmeasure consistency` (each primitive measured on every page of the lab); gates `pilot` and `book` refuse either failing. Layout: [14-module-layout.md](references/14-module-layout.md).

## Decide without asking (owner, 2026-11-24)
These come up in every build. Decide them yourself by the rule below, apply it, and state the decision in the report; never stop to ask.
| Situation | Decision |
|---|---|
| The generated palette CSS of the module trips the host's colour/token guard | Add **one** exemption for that file, in the guard, with a comment that it is generated by `pdfmeasure palette` (rule L12 keeps it generated). One palette file per module; nothing else is exempted. |
| Fonts: the printed face is not available (outlined text, commercial face, a brush or handwriting face) | Choose by the typography spec, not by eye: try faces the project already ships, then open-licensed faces (SIL OFL, e.g. a `@fontsource` package), and keep the one with the best `typography --url` scores (`size`, `weight`, `family`). A brush or handwriting sample (high stroke contrast in the spec) gets an open-licensed brush or handwriting face. Report the face, its licence and its scores. |
| Output kind | `web-fixed`, the default: desktop (print sheet) and mobile (reading view) are **both** required and built together. `reflow --auto-url` must show the reading view at 360 px and the sheet at 1280 and 1920 px. |
| Text of the sample pages | Write original sample content for the lab and tests (never the book's text in the repository). Real book content reaches a product only through the product's content source at run time (database, import, CMS), never committed. |

## Setup in a project (once)
`python3 <skill folder>/scripts/init.py` (Python 3.10+ only): checks the environment and prints the install command for each gap, registers the Stop hook in the project's `.claude/settings.json` (merged, idempotent), adds the output folders to `.gitignore`, reports whether the UI stack is supported. `--check` writes nothing. Run it when the skill is first used in a repository, and tell the user what it reported.

## What you need
- `pdfplumber`, `numpy`, `Pillow` (Python 3.10+), `pdftoppm` (poppler-utils), Node 18+ with `playwright` (+ its browser). `scripts/requirements.txt`.
- A dev server that renders your rebuilt pages (any framework) with `data-wb="<id>"` style attributes on measurable elements (see `references/05-build.md`).
- Run the tools from `scripts/`: `PYTHONPATH=. python3 -m pdfmeasure <command> ...` (use `python3`, not `-I`, or PYTHONPATH is ignored). Tests: `PYTHONPATH=. python3 -m pytest tests -q`.
- Copyright: never commit the PDF, its images, characters or text. Commit only measurements, configs and original fixture content.

## Pick the workflow first (do not run everything by default)

| The user asks for | Do | Skip |
|---|---|---|
| Analyse the PDF | phases 0–1 | the rest |
| List the objects a page or cover needs | phases 0–2A (inventory); done when `INVENTORY_COMPLETE`, rows may stay `TODO` | build, verify |
| Build a page (or pages) in React | 0–6, then 7–8, then **Visual QA** (phase 10) before saying it is done | nothing |
| Check a page that already exists | 7–8, then Visual QA + triage + report (repair only if allowed) | 0–6 if the configs still match |
| Replicate a whole book | all phases, page type by page type, **under the harness** | nothing |

Any build (not analysis-only) starts with `state init` and ends with `gate delivery`: see [10-harness.md](references/10-harness.md). Choose the output kind (analysis / replica-lab / web-fixed / web-reflowable / epub-fixed) and the pilot pages before phase 5.

Reuse earlier results while they are still valid (an up-to-date `roles.json`, `object-inventory.md`, tokens). Free choice where the task is open (what to draw, how to structure components); strict where accuracy is claimed (numbers come from the tools, never from your eye).

## Step by step

### Phase 0 — Inspect and classify
(Builds: after step 3 below run `state init` with the output kind, the pages and the pilot pages; see [10-harness.md](references/10-harness.md).)
First decide the PDF type (vector + text layer / outlined text / scan / mixed): it decides which tools apply (see [01-inspect.md](references/01-inspect.md)). A scan has no vectors: skip the vector commands (`shapes`, `signatures`, `roles`, `report`, `palette`) in phases 1–3 and do the inventory (2A) by sight only; say so.
1. `python3 -m pdfmeasure shapes --pdf X.pdf --pages 9-13` lists vector shapes per page (kind, bbox in pt, fill, stroke, linewidth). Run with `--glyphs` to see outlined text.
2. Confirm: page size (pt), whether text has a text layer (print PDFs usually outline text, so text *content* is not extractable but its ink position is), which pages are the template pages vs covers/answers.
3. Render a reference raster: `pdftoppm -r 100 -png -f 9 -l 9 X.pdf out/p`. Look at it. Decide the page list and left/right pairing (`--first-side left|right`: the parity of the first page; margins and decorations mirror between sides).

### Phase 1 — Page analysis
Goal: what is identical on every page and what varies. Use `report` to turn per-page shapes into invariants after phase 2, but start by eye on the raster: running header, tab, card/frame, margins, columns, footer, binding-side decorations. Write `layout.md`: regions with coordinates in pt, which side they mirror to. Never begin with components; begin with the page frame.

### Phase 2 — Inventory components
1. `python3 -m pdfmeasure signatures --pdf X.pdf --pages 9-40` groups shapes by signature (kind, coarse size class, fill, stroke, line width) and lists pages where each occurs. Frequent signatures are template parts; one-offs are content.
2. Name each recurring signature as a **role** and write a rule in `roles.json` (kind + colour + size ranges). `python3 -m pdfmeasure roles --pdf X.pdf --pages 9-13 --rules roles.json` prints the roles each page matched; to find unnamed shapes compare it with the `shapes` output of the same page (the command does not list leftovers or double matches) and iterate until the template parts are covered.
3. List components (tab, card, speech bubble, word bank, example box, table, hatch band, icons…) with their parts and variants in `components.md`.

### Phase 2A — Visual object inventory (mandatory before building)
The tools see vector shapes, not what a picture shows. Look at every page yourself **on high-zoom tiles, not on the whole page**: run `tiles --mode pdf` (≥ 6 px/pt, each picture small enough to be viewed unscaled, blank tiles skipped, box in pt on every tile) and look at every tile. A whole page at 1.4 px/pt (`pdftoppm -r 100`, fine for orientation only) loses the small parts: numbered stroke-order circles, arrowheads, dotted guides, hairlines, brush taper. List each small part as its own row (or as a named sub-object of its illustration). Keep `object-inventory.md` (ID, page, object, region, approach, status `TODO|DONE|VERIFIED`). It is a coverage checklist, not a detection system. Details, completion contract and evidence rules: [03-inventory.md](references/03-inventory.md#phase-2a--visual-object-inventory-agent-driven).

### Phase 3 — Measure per component
1. `python3 -m pdfmeasure report --pdf X.pdf --pages 9-40 --rules roles.json --quantities quantities.json --out report.md` gives each quantity (position, size, radius, stroke width, tail length…) as a value per page with spread; a quantity with spread ≈ 0 is a template constant, a larger spread means a variant or per-page spacing.
2. `python3 -m pdfmeasure palette --pdf X.pdf --pages 9-40 --rules roles.json --out workbook-palette.css` converts the CMYK fills/strokes (poppler interpolation, same as a PDF reader shows) to sRGB hex custom properties.
3. For text: do not read glyph shapes. Measure line positions (`lines`), and later pitch and word edges in phase 8.
4. **Typography spec (mandatory before building a page):** `typography --pdf X --page N --output O --spec-only` (8 px/pt) gives per text style the core height, stroke width, weight (stroke / core), contrast (gothic ~1, myeongjo/serif > 1), ink proportion, line pitch and the left edges (indents) in use, plus the exact font names and sizes when the PDF has a text layer. Choose font family, size and weight from these numbers, not by eye: without a text layer, render a candidate in the lab and scale the CSS size by the core-height ratio. Details: [04-measure.md](references/04-measure.md).
4. Record special geometry by hand in `components.md` (e.g. bubble tail base, fold corner, hatch period and angle, shadow offset), always in points.

### Phase 4 — Models
Three files, no markup: **tokens** (every measured number in pt, named, with its source page), **content model** (Zod/TypeScript schema of what a page contains: sections, items, glossary…), **fixtures** (original sample content — never the book's text). A part must read its look only from tokens and its data only from the content model.

### Phase 5 — Apply (build parts)
Follow `references/05-build.md`: the sheet is a container with `--wb-pt = 100cqw / pageWidthPt`; every length is `calc(N * var(--wb-pt))`; strokes and curved outlines are SVG with `vector-effect` off and stroke centred on the path; colours come from the generated palette CSS (one token-guard exemption). Put `data-wb` ids on measurable elements.

### Phase 6 — Re-architect
Follow the module layout of [14-module-layout.md](references/14-module-layout.md), built for many books even with one: shared `core/` and one style pack per book under `books/<id>/`, CSS scoped by `[data-book=<id>]`, books loaded lazily (checked by `pdfmeasure structure`, required by gates `pilot` and `book`; declare it with `state module --path <module> --book <id>`). In short: every repeated pattern is one kit primitive (contract in `core/kit/contract.ts`, reading implementation in `core/kit/reading/`, one implementation per book in `books/<id>/kit/`); block renderers are written once in `core/blocks/` and compose primitives without drawing anything; `core/views/page-view.tsx` maps the content to blocks; a lab route shows every fixture page in both views. Remove duplicated geometry; per-question spacing the page did by hand becomes an explicit `layout` hint in the content.

### Phase 7 — Verify layer 1 (geometry in points)
`python3 -m pdfmeasure verify --config verify.json --pdf X.pdf --out out/` runs, per page: `measure-dom.cjs` (browser: real element boxes at a huge scale so Chrome's pixel snapping vanishes), then `compare` of every check (PDF role field vs DOM element field, or expected literal) with a tolerance. Outputs `geometry.md`. Every row must pass (typical tolerance 0.1–0.3 pt). Fix model or part, rerun.

### Phase 8 — Verify layer 2 (zoom per part)
Same command also runs `zoom`: for each part box (whole-point `[x, top, w, h]`) it crops the PDF at 12 px/pt and the rebuilt sheet at 12 px/pt, then compares by a method: `align` (register by colour mask, report shift), `ink`, `extent`, `line` (thickness and centre), `lines` (line bands), `words` (word edges for identical strings), `columns`, `pitch` (letter pitch by first-harmonic autocorrelation). Outputs `zoom.md` with side-by-side images. Look at the images, not only the numbers.

### Phase 9 — Package
Write `layout.md`, `components.md`, `architecture.md`; keep `geometry.md`/`zoom.md` as generated evidence; add the palette file to the repo's colour-guard exemption; unit-test tokens and the model schema; do not register a dev lab as a product screen.

### Phase 10 — Visual QA and repair loop (after building, never for inventory-only tasks)
Look at the whole page, not only the measured parts. **Scan once, get the whole error report, fix in the same run, scan again once:**
1. `visual-compare --label v0 --verify-config verify.json` writes `scan-v0.md`: every different region with its crop, registration warnings and the failing geometry/zoom entries, in one pass. Do not re-run comparisons to discover errors one at a time.
2. Look at the page image, heatmap and every crop; the scan only *locates* differences at 3 px/pt: judge details on `tiles --mode pair` (PDF | rebuilt, ≥ 6 px/pt), made after the scan and before `state view`; triage all real defects together (`issue add-batch`, severity P0–P3 is your judgement, stable IDs).
3. **Fix them in this same run (P0 first), not just record them.** Fixing what React/CSS/SVG/tokens can fix is part of the build task; stopping at a defect list or a Codex prompt is not finishing. Add a measured check or zoom part for each fixed defect so it cannot return.
4. `visual-compare --label v1` gives `triptych.png` (PDF | V0 | V1) and progress against V0; read `regression`, new regions and the failing entries; repeat only while P0/P1 remain and there is progress.
5. Hand to Codex only defects you tried to fix yourself and could not, each with a cause and acceptance criteria; keep the prompt files if the CLI is not usable and never claim Codex ran when it did not.
6. `VERIFIED` needs your visual check plus evidence, never an improved number alone; a page with an unresolved P0/P1 is not complete. Then `qa-report` and `qa-finish`. The output folder holds copyrighted page images: never commit it. Details and commands: [09-visual-qa.md](references/09-visual-qa.md).

### Harness (mandatory for every build, [10-harness.md](references/10-harness.md))
`state` and `gate` turn the rules above into checks the files must pass. In short: a page starts only with a `typography --spec-only` result and is `VERIFIED` only with a `typography --url` result newer than its scan and without ERROR; `gate inventory` needs `tiles --mode pdf` (≥ 6 px/pt) for every page and `state view --view-kind inventory` after them; a page is `VERIFIED` only with `tiles --mode pair` made after its scan; no page starts before `gate inventory`; only pilot pages start before `gate pilot`; a page is `VERIFIED` only when its scan is clean, you recorded `state view` after that scan, and no P0/P1 is open; an issue whose fix failed 3 times leaves your loop for Codex or BLOCKED; `gate book` re-reads every page's evidence; `gate delivery` also needs `qa-finish`, a report, no tracked book files and a green build. A Stop hook blocks ending the session with pages IN_PROGRESS or P0/P1 open. Say "gate not run" for any gate you did not run.

### Typography confirmation is mandatory (phases 7–8 and 10)
`typography --pdf X --page N --output O --url LAB_URL` scores every text style of the rebuilt page against the PDF on **size, weight, family, indent and line spacing**: PASS ≥ 95 %, WARNING < 95 %, ERROR < 92 %. The worst style and attribute decide the page. An ERROR blocks `VERIFIED`; a WARNING is allowed but stays listed (record it as a P2 issue with its cause). With fixture text add `--different-text` (indent is then not scored and is checked by geometry). Never relax the levels; when the right font is not available, say so and accept a limitation with the measured score. Details: [06-verify.md](references/06-verify.md#typography-confirmation).

### Text layout of every line is mandatory (phases 7–8 and 10)
Line spacing and left indents decide whether a book looks right, and part-by-part checks only cover blocks somebody declared. So `verify` also runs `text_layout` for every page: every text line of the PDF against every text line of the rebuilt page (left edge/indent, top, bottom, pitch to the line above, missing or extra lines), defaults 0.5 pt (left, vertical) and 0.3 pt (pitch). A page entry in `verify.json` must carry `"text_layout": {}` (optional `regions`, `colours`, tolerances) or skip it with a written reason; a replica that uses the printed text must not skip it. `visual-compare` runs the same check in every scan. Never loosen a tolerance to get green; an indent or a spacing that is off is a defect (P1 for a whole block). Details: [06-verify.md](references/06-verify.md#text-layout-every-line-mandatory).

### Artwork (characters, objects, scenes): describe, hand over, fit ([11-artwork.md](references/11-artwork.md))
Drawings are never traced or copied, and they are not left as gaps either. Mark them `artwork` in the inventory; `artwork brief` measures box, aspect, minimum size and palette; you fill the set-level `common` fields once (context, style for people, style for objects, night rule) and per object the identity, action, states, a decided `text_in_art`, and for **every person in the picture, characters and scenes alike, the origin (country/culture, with the clue) and the skin tone with a measured hex** (foreign-language books show many peoples on purpose; keep that mix); the same picture printed twice is drawn once (`reuse_of`); `artwork prompt` refuses an incomplete brief and writes a table prompt with the delivery contract (separate branch, `artwork-delivery/<set>/`, manifest, no merge). **Guide the user in the chat**: send the prompt and the numbered next steps, ask for the branch name. When they give it, `artwork import` validates and copies the files without checking the branch out, then fit them at their boxes. A page with undelivered artwork cannot be VERIFIED; while waiting, work on other pages or `state block` with the reason.

### Reading view on phones ([12-reflow.md](references/12-reflow.md))
The print-sheet view is for matching the PDF; on a 360 px phone its body text shrinks to about 6 px. A web ebook (`web-fixed`, `web-reflowable`) also renders the same content model as a **reading view**: one column in reading order, body 16–18 px with the typography spec's ratios, captions ≥ 14 px, wide grids wrapped, dialogues stacked, art scaled, zoom never disabled. Both views mark blocks with `data-block` (and non-body text with `data-text-role`). The reading view is the app's design and lives in the shared core (one renderer per block kind for every book); each book adds only its print-sheet renderers and CSS ([13-react-shadcn-tailwind.md](references/13-react-shadcn-tailwind.md)). `reflow --url <reading> --fixed-url <print>` checks it in a real browser at 320/360/390/768 px and saves screenshots; an ERROR blocks VERIFIED. Look at the screenshots and send them with the page report.

### Knowhow register: defects that come back ([knowhow.md](references/knowhow.md))
`references/knowhow.json` (rendered to `knowhow.md`) keeps the defects earlier builds hit, each with symptom, cause, fix, check and, where a source pattern gives it away, a detector (e.g. KH-001: a line under 1 CSS px drawn as a border is painted 1 px; draw it as an SVG stroke). In every build, without asking:
1. Before building a part, read the entries of its tags: `knowhow list --tag lines`.
2. When triaging a defect, `knowhow search "<symptom words>"`; link the issue to the entry it matches (`issue add --knowhow KH-001`, or a `knowhow` field in `add-batch`) and apply the documented fix.
3. After a fix is VERIFIED: an entry that matched gets `knowhow seen --id KH-nnn --build <book>`; a general defect with no entry gets `knowhow add --file entry.json` (title, tags, symptom, cause, fix, check, detector when a pattern gives it away). Specific to one book: no entry. New evidence that an entry is wrong: `knowhow update --id KH-nnn --file fields.json --reason "<what was measured>"`.
4. `qa-report` lists linked defects and the fixed ones without an entry (candidates); gates `pilot` and `book` run the detectors (`knowhow scan`) and refuse ERROR findings.
Commit `knowhow.json` and `knowhow.md` with the build: the register is how later builds learn.

### Results go to the chat (always)
Every run ends with a message to the user in the session chat, never silently: what was done, the verdicts (gates, typography, artwork import), what is open and why, and the pictures to review (attach the triptych or pair tiles of the pages changed, the report). When the user must act (run the artwork prompt, choose fixed or reflowable, give a branch), say exactly what to do as numbered steps.

## Report format
For every page: inventory rows VERIFIED / total (and any excluded with reason), geometry N/N, zoom N/N, plus the three or four residual differences you accept (e.g. different font) and why. Say "not verified" for anything not measured.
